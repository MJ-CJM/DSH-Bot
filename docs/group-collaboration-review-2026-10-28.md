# DSH-Bot 自然群聊优化方案

日期：2026-10-28。代码基线：`phase/deepening@b4cd01d`，插件 `0.4.1`。
原生 API 依据为只读 `deepseek-harness@dsh-v0.2.1-rc.2`；桌面宿主版本为 `0.2.1-rc.3`，运行兼容性须分别验证。

## 1. 产品方向

用户把几个已有 Bot 拉进群，直接聊天。Bot 根据各自能力接话、互相提问、接续处理，并把结果留在群里。
分工和评审可以通过聊天自然发生，由 Bot 根据实际需求决定。

本方案按用户最新要求修订，替代此前以任务流程为中心的建议：取消强制协调者、任务模式、计划卡、DAG、固定评审阶段，以及原生 Team 适配作为群聊前置条件。已有 Bot 的人设、技能、工具与权限继续生效。

核心改动是群消息的投递、上下文和接续规则，加上自然的聊天界面。后台继续记录执行、取消、去重和恢复信息，用户不需要管理这些内部状态。

## 2. Grok Bot 可以直接参考的体验

Grok 官方说明支持普通消息由 Bot 决定谁回应、@ 指定成员、引用回复定向原发言者，以及 Bot 间异步交接。群消息和私聊交接有不同的结果落点。[官方协作说明](https://docs.x.ai/grok-bot/chat-and-collaboration)

每个 Bot 保留自己的记忆，群内公开的是它实际发出的内容；入群不等于共享整个私人记忆库。[Bot 与记忆](https://docs.x.ai/grok-bot/bots)

本会话只读观察的 Grok 现有群里，多个具名 Bot 在同一时间线接续发言，成员与资料库放在群详情里。这可以作为 DSH-Bot 的界面参考。没有主动发起新任务，也未验证消息中声称已修改的文件。

Grok 未公开内部群调度算法。下面的消息路由和停止机制是 DSH-Bot 的实现建议，不能据此声称复刻了 Grok 内部实现。

## 3. 当前实现与具体优化

下列源码路径相对于 `packages/dsh-bot/`。

| 方面 | 当前实现 | 建议 |
| --- | --- | --- |
| 普通发言 | mention 模式无 @ 时，Client 不提交，Host 拒绝 | 默认允许直接发消息；Bot 可以回应，也可以明确选择不补充 |
| 指定成员 | 已支持 @、轮流下一位、全员一轮 | 保留 @；增加引用回复，把轮次选择移出主要聊天流程 |
| Bot 接话 | 一次选好成员，按顺序执行；后面能看到本轮前面输出 | 允许成员主动找同群 Bot，对方答完后原提问者能继续 |
| Bot 间通信 | `bot_message` 限精确 Bot 主会话；群 child 不能用 | 增加绑定实际群执行身份的薄消息桥，复用现有校验和回执能力 |
| 连续上下文 | 每次 fresh spawn，注入有界群历史 | 先修消息引用与前序结果选择；持久成员会话后续验证 |
| 聊天展示 | 回答包装在轮次与 deliveries 面板，主要结果 settled 后出现 | 按发言顺序显示头像、名字、引用、正文、文件；执行详情放次级入口 |
| 停止 | 当前取消单个 turn | 一次停止当前输入引起的整条自动接续；新用户消息仍能正常开始 |

### 普通发言和按需回应

路由优先级建议为：明确 @ → 引用回复的 Bot → 普通消息的参与规则。@ 菜单绑定真实成员 ID，避免重名和正文解析歧义。

首版可让小群中的活跃成员按现有顺序获得一次回应机会，并看到前面已有的回答；没有新增信息就选择不发言。
需要明确的 `skip` 结果，不能将空内容一律记为执行失败。现有完成判断见 `turn-runner.ts:88`。
这能先复用现有执行路径，但会产生每成员一次判断的成本。后续依据对话参与者、明确收件人和实际测量减少无关唤醒，不另加一个必需的协调模型。

Bot 普通发言可以对全群可见；明确向某成员提问或回复才追加对应唤醒。不要把每条 Bot 消息都再广播给所有模型执行一遍。
支持 @ 多人或全员，但一次通知中的重复成员只投递一次。

### 同群 Bot 互相接话

目标体验可以很简单：用户说“帮我看下这个方案”；A 发现数据不确定，在群里请 B 核实；B 回复；A 使用该回复继续给用户建议。
谁先回应、是否需要其他成员、是否需要评审，都由当次对话决定，不预置固定阶段。

建议为本插件创建的群 worker 提供 `group_message` 薄工具，输入仅包括接收成员、正文、回复引用和是否需要回信。
Host 绑定实际群、发言 Bot、执行 child 和消息来源，模型不能填写任意 Session 地址。工具通过公开 Agent 生命周期接入并纳入 `ctx.effect` 清理；身份绑定与 hook 时序先做小型验证。

保留原 `bot_message` 的主会话限制。直接放开 child 会把群请求导入私聊，也会破坏已有调用者校验。
共同的成员校验、数据出站检查、请求去重与回执尽量复用现有模块；不复制完整跨会话消息系统。
参考 `host/groups/data-flow.ts:25` 的 `groupChild/groupResult` 和现有 Messaging 服务。

投递接受后立即回执，目标 Bot 稍后响应；工具不能同步等待目标回答，否则会与当前按群串行的队列相互等待。
目标回复写回原群；有明确回复关系时，再唤醒原发问者一次。每次派发重查当前成员身份和取消状态。
自动接续的触发信息保留 `authorKind/botId/replyTo/causeId`，不得把 Bot 说的话重写成人类的新授权。

### 群上下文和共同结果

优先提供当前输入、引用的消息、已经完成的相关前序回复、相关产物引用，再加入有限历史。
群成员知道其他成员的名字和能力摘要，可以自己判断找谁；私人会话全文不自动注入群上下文。

源码推导存在一个需要复现的排队问题：`turns.ts:63` 在准入时固定 `contextThroughSeq`，随后排队；
若 B 在 A 完成前入队，A 稍后的结果可能超过 B 的截止线，而 `turn-runner.ts:45` 的 previous 只包含 B 本轮输出。
修复应纳入明确的前序结果，同时保留“A 看不到之后排队的 B 输入”的现有约束，不能简单改成读取全部最新历史。

文件和截图通过群消息中的可打开引用共享，按需在群详情聚合为资料库。文件本体复用原生文件/附件能力；不增加必填交付物表单。
Bot 获得资料引用不代表自动获得文件权限，也不代表整份长期记忆已共享。

### 停止和恢复

用户按“停止”后，取消当前自动接续链的未开始请求，abort/dispose 在途 activation 并等待清理；迟到结果不能再启动其他 Bot。
已经完成的消息和文件保留。新用户输入建立新的响应链，旧链不随刷新或新输入复活。
后台以消息 ID、接收成员和执行代次去重，限制连续唤醒次数和总时长；可调项进入导出的 Config 与 schema。

原生子 Agent 容量限制会拒绝请求，不负责等待派发；继续复用本包轻量消息队列，保证每成员执行有序。
重复失败、来源不明或受理结果未知的执行进入可见的待恢复状态，不自动重发可能已产生副作用的操作。
这些规则支持普通聊天，无需让用户理解内部 turn/delivery。

## 4. DSH 官方能力复用

| 需求 | 复用能力 | 插件保留的职责 |
| --- | --- | --- |
| 成员身份和执行 | 已有 Bot preset、`ctx.subagents.startActivation`、`agentPreset/agentOptions` | 选择成员，拼接有界群上下文 |
| 完成与取消 | activation.result/dispose、AbortSignal | 将结果写回群，取消后禁止后续唤醒 |
| 消息与恢复 | 原生 Session/持久化及现有 groups 存储 | 群地址、回复关系、去重和处理进度 |
| 工具和审批 | 原生工具执行、ask/deny、既有技能/MCP/credentials | 显示谁在等待及原生入口；Bot 发言不产生新的用户授权 |
| 内容和界面 | 原生文件/附件、公开 slots；公开渲染接口需逐项核实 | 群消息视图与产物索引，不导入内部 Client 组件 |
| 定时及高级任务 | 原生 schedule、Agent Teams | 有实际需要时接入；自然群聊不依赖 Team 任务板 |

首版继续复用现有 `spawn + delivery:'caller' + 独立 preset + 有界群历史`。它提供对话信息的连续性，不能描述为同一个运行中 Agent 永久续聊。
fresh child 不保留上轮私有执行上下文，每次仍须提供相关群历史；成员阅读游标只负责触发和去重，不能替代上下文。

每群每 Bot 的原生连续会话可作为后续优化，但锁定版本有以下边界：

- `startActivation({childId})` 为新建预留 ID，不是恢复旧 child；复用旧 ID 会冲突。
- 公开 `subagents.sendMessage` 只允许精确 live sender 对直接父/子发送；同群 sibling 不能直接互发。
- 公开 `subagents.prompt` 面向浏览器用户，生成 user 来源，不能用来伪装 Bot 自动发言。
- cold resume 路径未保留初始 caller delivery，默认 parent 通知与当前 no-model 群根的组合需要实测。
- 保留自定义来源的内部投递接口不在可用公开入口中，不从内部路径绕过。

依据：参考仓库 `packages/subagent/subagent/src/index.ts:298,429`、`manager.ts:425,934,1188,1362`、
`types.ts:31`、`internal.ts`；本仓库 `host/groups/root-guard.ts:6`。
因此连续会话的 API spike 不阻挡首版自然群聊，也不通过自建 Agent runtime 解决。

原生 Team 继续作为可选能力保留。其 `spawnTeammate` 尚无 agentPreset 参数，普通 spawn child 也不自动成为 durable teammate；
不为解决这个差异强行重构群聊。将来确需原生任务板，再复用 `ctx.agentTeams` 的任务、CAS 和依赖能力。

## 5. 落地顺序

| 批次 | 改动 | 验收重点 |
| --- | --- | --- |
| 第一批 自然聊天 | 普通消息可发、@/引用回复、显式 skip、平铺时间线、修复前序上下文 | 用户无需选择模式即可交流；不重复回答；后续提问承接已有内容 |
| 第二批 Bot 互聊 | 群作用域工具、异步消息接续、来源校验、去重、整链停止 | A 找 B，B 回复，A 接着处理；全程在同群；不会死锁、无限互叫或跑到私聊 |
| 第三批 体验和效率 | Markdown/代码/附件、群资料库、忙碌状态、按需并行、续聊 API spike | 结果可查看；无关成员少唤醒；刷新恢复可靠；连续会话仅在公开 API 验证后启用 |

第一、二批共同构成“多个 Bot 能自然群聊”的最小交付。单独完成第一批只改善交互，不能声称 Bot 已可自主互相协作。
各批独立保留开关和旧记录兼容性；不新建通用流程引擎，不要求用户迁移到任务模式。

已有 `gateway/definition-unavailable` 的错误分类、草稿保留和重启提示可独立改进，不必绑定群聊改造。
当前插件运行/刷新正常的证据，不替代新增群聊验收。

## 6. 验收场景

1. 建群后直接发送普通问题，无 @、模式选择或计划表单也能得到回应；无补充的成员保持安静。
2. @ 和引用回复准确找到成员；重名可区分；显式 @ 优先于引用；跨群引用被拒绝。
3. A 在群内找 B 核实，B 回答，A 使用该结果继续；来源和产物能对上，A/B 私聊不被污染。
4. 排队追问包含已完成的相关前序结果；旧执行看不到未来输入；历史截断仍保留当前引用。
5. 停止覆盖在途与待接续；迟到结果不复活；停止后发新问题正常。
6. 相互重复提问会有界停止；重试不重复发消息；已受理不误写成已完成。
7. 刷新或重开后消息、成员、引用、草稿和停止状态一致；unknown 不自动重放副作用。
8. 在真实 DSH 验证时间线、@ 菜单、回复条、内容渲染、停止和原生入口；检查中英、亮暗及窄屏。

实现阶段先用确定性 Host/工具测试验证路由、取消、幂等与上下文，再做实际 UI 和获授权的真实模型对话验收。
模型效果观察重复发言、人工中转、结果正确性、耗时和调用成本，不以 Bot 发言数量或自称完成计分。
