# DSH-Bot 主动职责与交付体验设计

本设计定义未来产品行为，不表示当前版本已具备这些能力。总体决策见[完整设计](README.md)，底层数据与协议见[技术架构](architecture.md)。

## 1 用户需要完成的工作

DSH-Bot 面向有持续项目责任的使用者。Bot 的价值不只在于回答一次问题，也在于记住职责、识别下一步工作、组织执行、报告可核实的结果。用户仍然能够直接聊天和发起群任务；主动能力通过职责逐项开启。

| 编号 | 用户需要 | 第一版交付结果 |
| --- | --- | --- |
| U01 | 告诉 Bot 长期关注什么 | 有名称、范围、期限、模式和预算的职责 |
| U02 | 知道 Bot 为什么提出建议 | 原始事件、变化、相关职责、建议动作与验收条件 |
| U03 | 避免重复通知 | 同一事项归并，普通事件静默，建议有冷却和有效期 |
| U04 | 一次接受后持续推进 | 一个任务身份跨执行、等待和返工，展示下一步与阻塞 |
| U05 | 让多个 Bot 合作 | 现有群成员与执行过程可见，主管汇总交付 |
| U06 | 控制能做什么和花多少 | 行动范围、工具权限、数据范围、期限及三类预算 |
| U07 | 判断任务是否真的完成 | 每个验收项对应产物版本、命令/观察和证据 |
| U08 | 停止后续工作 | 暂停职责、停止任务、撤销授权分别生效，显示已发出和未知动作 |
| U09 | 关掉应用再打开后了解发生什么 | 来源游标、任务与收据恢复；不确定运行明确待核对 |
| U10 | 让 Bot 以后少犯同类错误 | 反馈形成可预览、评估、采用和撤销的候选 |
| U11 | 在需要时从 IM 获取结果 | 复用通知政策与社区渠道桥，外发正文与目标另有授权 |
| U12 | 用专项工具完成复杂任务 | 在能力矩阵允许时调用外部执行器，显示外部状态和成本 |

U01–03 属 M1，U04–09 主要在 M2/M3，U10–12 在 M3/M4，不能仅凭页面实现将这些故事标成完成。

## 2 信息架构

保留现有 Bots、最近对话、群管理、记忆、连接器和定时任务入口。主动工作台是这些能力的任务视图，不另做完整聊天应用。

| 位置 | 内容 | 复用关系 |
| --- | --- | --- |
| Bots 目录 | Bot 名称、职责摘要、是否暂停、需要处理的事项数 | 复用目录和 catalog；不逐行加载全部任务与 Session |
| Bot 详情的“职责” | 关注来源、触发条件、模式、权限范围、预算、验收模板 | 在现有 Bot 设置体验内新增业务字段；和连接器配置分开 |
| “待我处理”工作台 | 待接受建议、请求决定、待验收交付、待核对运行 | 使用公开 main/侧栏 slot；复用原生组件和主题 |
| 任务列表与详情 | 目标、当前进展、运行入口、证据、评审、成本 | 从核心和现有服务生成只读视图，不保存第二份任务状态 |
| 群的活动视图 | 与任务相关的 turn/delivery、成员运行和统计 | 链接现有群管理/原生会话，不复制执行过程 |
| 通知中心 | 汇总提醒、发送结果、已读状态 | 现有 Notifications 管运输；工作台管需要人处理的事项 |
| Bot 详情的“改进建议” | 职责/偏好/Skill 的修改候选及对照结果 | 采用后进入相应现有配置/记忆流程 |

“待我处理”不是通知存储：建议即使在静默期间也可以被用户主动查阅；是否弹出提醒或外发是另一项决定。进入工作台不调用模型。空列表解释当前无待处理事项，并展示最近一次来源同步时间；不提供自动发送的演示任务。

UI 遵守现有公开 View ID 的唯一性，不注册第二个原生 chat/trajectory，不调用父组件私有 selectView。新图标、输入、Menu、Tabs、状态点优先使用已验证的公开组件；所有文案中英同键，颜色使用现有 `--dsw-alias-*` token。浏览器必须检查亮/暗主题、窄屏、键盘与焦点恢复。

## 3 职责配置

用户配置五组内容，界面先给有意义的模板，再允许细化。自然语言用于描述意图，边界由结构化字段约束。

### 3.1 关注事项与来源

示例：“关注 DSH-Bot 主分支的 CI 失败，并建议修复；一项任务完成后提供测试证据。”

来源选择必须展示类型、账户/连接器、精确项目与分支、可读内容、最近同步和能力状态。凭据只保存现有 credential reference。默认不扫描全部磁盘、收件箱或其他 Bot 记忆。

来源最小集合：M1 一个 GitHub CI 只读适配器加离线夹具；M2 接入本项目执行结果；之后才扩展文件/交付证据、Issue、研究来源与 IM。原生 webhook 已认证只说明收到来源消息，持久受理与去重仍要验证；暂不可接入时显示原因，允许手动同步已授权来源。

### 3.2 介入条件

结构化条件包括事件类型、状态变化、标签、路径范围、严重程度、最大事件年龄与排除条件。先执行确定性规则，再决定是否需要模型研判。

“继续关注”需要可解释的恢复条件，例如 CI 新结果、截止日期或对方回复。不能保存一个没有来源或检查方式的“以后看情况”。未来条件提醒要有作用范围和过期时间；会话内提醒不暗中启动后台轮询。

### 3.3 行动模式与范围

| 模式 | 发生什么 | 不隐含获得的权限 |
| --- | --- | --- |
| 关闭 off | 保存配置；不摄取此职责的新事件、不研判、不新派工 | 不自动取消另一职责或用户直接发起的任务 |
| 只建议 suggest | 读取已授权来源、必要时研判、形成建议 | 不自动修复、派群任务、发外部消息 |
| 有界自动 auto | 仅对匹配预授权的动作自动接单并执行 | 不扩展工具、目标、数据共享、成员或费用上限 |

模式是 DSH-Bot 产品契约，不能直接作为原型 off/observe/auto 的无损映射。尤其原型 observe 可能运行模型，明确请求在各种模式下也可能执行。适配器在职责入口控制摄取与自动派工，用户主动聊天仍走现有权限路径。

可选择的动作类别逐项开放：只读分析、隔离工作区修改、测试验证、外部通知、外部写入。M1 只读，M2 人工接受后允许限定修改与测试，M3 才开放配置完成的白名单自动动作。动作模板没有通过兼容性与数据边界验证时不可选择。

### 3.4 预算与期限

预算分为：研判预算、执行预算和注意力预算。每项显示已用、预留、可用、计量是否完整和下一次重置时间。费用未知显示“未知”，不能显示 ¥0 或 $0。

研判预算用次数和 token 上限双约束；执行任务使用 token、最长运行时间、并发和总尝试次数；注意力预算使用建议提醒次数和打断次数。钱可以作为额外上限，只有具备可靠计费信息时才启用。外部执行成本另列，不能混入原生 Session 的 token。

预算持久预留后再发起工作，回报据真实计量结算。未知运行保留预留，不因重启或删除任务立即退款。修改时区不能使当天预算重置。超限后结束当前可控步骤并显示“额度不足，等待决定”，不以摘要压缩或更换模型绕开总额。

### 3.5 通知和验收

设置时区、静默时段、普通提醒上限、同事项冷却和允许的渠道。紧急打断必须独立开启，并定义可匹配的紧急事件；模型单方面声称“紧急”不能越过静默。

验收模板由目标、交付物和检查项组成，例如：修改限定目录；新增用例复现原错误；相关测试通过；列出未覆盖项。检查是需要工具证据、人工判断还是二者都要，必须在接单时区分。任务开始后更改验收要求产生新版本，旧证据不能默认为满足新要求。

## 4 建议的默认值与配置归属

以下为新功能的初始设计值，需要在 PB00/PB01 固定契约，在试点后调优；不是当前已存在的 Config 字段。已有 schedule、通知、连接器参数继续由原服务拥有，适配层只读取/引用，不能复制为两份互相覆盖的配置。

| 拟定参数或策略 | 初始值 | 理由与边界 |
| --- | --- | --- |
| proactiveEnabled | false | 插件升级不自动开始摄取、研判或行动 |
| responsibility.mode | off；用户开启时默认 suggest | 保存与启用分开，首次启用展示读取范围和模型成本 |
| triageConcurrency | 每 Bot 1，Host 2 | 同事项由核心串行化，并发上限不能替代线程互斥 |
| executionConcurrency | 每 Bot 1，Host 2 | 避免后台挤占交互任务；也受原生可用能力限制 |
| triageDailyLimit | 每 Bot 20，Host 100 | 次数上限独立于 token/费用上限，任一耗尽即停止新研判 |
| maxTriageTokens / maxTaskTokens | 首次启用必须设置有效上限，无无限默认 | 绑定计量能力；无可靠计量不开放 auto |
| maxTaskAttempts | 3 | 总派工尝试而非每成员无限重试；失败原因需可重试 |
| maxTaskWallTime | 首次接受/自动规则中明确设置 | Host 停机不重置期限；等外部条件不保持模型忙等 |
| suggestionTtl | 24 小时 | 到期保留审计摘要，但接受前重新取事实与策略 |
| attentionDailyLimit | 每 Bot 3 次主动提醒 | 合并成批次计提醒，展示合并事项数量；限制不能通过改频道绕过 |
| attentionItemCooldown | 同事项 6 小时 | 任务出现新的阻塞/交付版本可生成新事项，仍受日限 |
| quietHours | 22:00–08:00，首次启用明确 IANA 时区 | 可建议已有用户时区，不推断本机时区就是用户意图 |
| normalTriageInQuietHours | defer | 低成本认证/去重继续，普通模型研判与提醒延后 |
| autoPermission / externalEgress | 无默认授权 | 限定任务、动作、目标、数据范围、版本、有效期与预算 |
| schema / retention | 有显式版本和保留配置 | 去重 tombstone 不短于来源最大重放期；正文与标识分开 |

职责层只能收紧 Host 配额。任务只能收紧职责范围；它不能修改 Host 工具权限。产品模式、Host 可用性、原生运行权限、数据出站许可分别展示，避免“auto 已开启”掩盖某个实际不可用的能力。

## 5 建议卡片和人工接单

卡片至少包含：发生了什么、观察时间、职责名称、可点击来源、为什么需要处理、计划动作、预计成本范围、验收条件、建议有效期。默认展示摘要，日志和可能包含敏感信息的正文按当前权限展开。

| 用户操作 | 业务行为 |
| --- | --- |
| 接受 | 重新读取来源/职责/权限版本，创建一次接单；重复点击返回相同结果 |
| 调整后接受 | 修改目标或范围形成新提案版本，再准入；不能沿用旧批准摘要 |
| 暂不处理 | 选择明确提醒时机或未来条件；不创建空转任务 |
| 忽略本次 | 记录理由，关闭本事项；不自动屏蔽该来源的所有未来事件 |
| 不再提示类似事项 | 生成职责规则修改预览，用户保存后生效 |
| 查看来源/运行 | 进入现有来源或原生会话；不触发新执行 |

接受需要当前客户端动作与 Host 服务验证相配合，不能用 `source.kind=user` 字符串当作可信人工授权。M2 的批准桥必须经 PB00 的原生 approval/入口实验。无法取得所需执行或数据批准时，保留建议并说明缺少什么能力。

并发场景：另一端已经接受时打开同一任务；事件已恢复时提示新状态并撤销过时动作；Bot 删除重建、成员变化、来源或职责范围变化时使旧建议失效；网络超时显示“正在核对是否已接受”，不能换 ID 再次接单。

## 6 任务详情和持续工作

任务详情首屏按阅读顺序呈现：目标与当前结论、下一步或等待原因、需要用户做的事、交付与证据、执行过程、预算和来源。机器内部状态不直接占据标题。

| 产品显示 | 条件 | 用户可以做什么 |
| --- | --- | --- |
| 等待执行 | 已接单，尚未获得有效派工能力/并发 | 看排队原因、调整范围或停止 |
| 正在处理 | 精确 Assignment 有正在运行的原生执行 | 查看成员过程、停止后续动作 |
| 等待条件 | 当前执行释放，等待指定事件或截止点 | 查看等待对象、补充信息或停止 |
| 需要决定 | 权限、预算、需求冲突需要用户判断 | 对准确问题作决定，不无限延长既有授权 |
| 待核对 | 派工/工具/通知结果不确定 | 查看可核对证据，确认前不自动重放副作用 |
| 待验收 | 某交付版本已提交，检查结果完整展示 | 接受、按具体项返工、补证据 |
| 已验收 | 版本化验收记录通过，所有必需项有证据 | 查看成果、发起新的工作 |
| 已停止 / 已失效 | 用户停止或身份/策略条件失效 | 查看已发生动作；恢复需要重新核验 |

这些是可重建显示状态，由核心任务、执行收据、验收记录共同投影；客户端不能直接写 status。原型 ready/ended 的具体映射在 PB00 固定，如果需要扩展只修改任务核心一处。

同一任务等待新事件后可以建立下一 Assignment。已有成员会话是否可继续，依据原生 provider 能力和当前代际；rc.2 不支持的冷恢复不能假装继续同一个执行。会话可以新增，任务身份与历史证据应连续。

主管默认先评估单 Bot 是否够用。需要并行研究、独立验证或明确角色分离时使用现有群能力；成员角色、轮次上限、总预算在接单范围内。新成员或新的权限要求不能由模型自行扩展。一个成员失败可以给出部分交付，必需验收项仍为失败，不把其他成员成功数抵消该失败。

## 7 成果、验收与返工

交付版本包含：目标、变更摘要、产物引用与内容指纹、执行范围、逐项证据、未执行项、已知风险和可复现步骤。内容引用必须关联精确 Git commit/worktree 状态或文件摘要，单纯“最新报告”链接不足以证明本轮成果。

验收项使用 PASS / FAIL；未执行为 FAIL(NOT_RUN)，环境受阻为 FAIL(ENVIRONMENT)，证据过时为 FAIL(STALE)。可以另有人工决定 pending，但不能用 pending 统计成通过。

证据层次明确：

1. 源码/静态检查：只支持结构、类型或规则结论。
2. 构建/单元测试：支持对应产物与用例的结论。
3. 安装/启动：支持在指定环境中成功启动。
4. 真实浏览器/设备操作：支持实际观测流程。
5. 独立业务验收：判断目标是否满足，并记录验收者与版本。

自动检查使用固定或明确获准的验证工具与只读结果解析，不执行来源正文或模型临时拼出的任意“验收脚本”。执行者可以提交候选检查结果，独立验证器/人工决定是否采纳；验证器本身的权限与预算也受任务约束。

返工指出失败项、期望和仍然有效的证据，在同一任务创建新的交付版本。旧证据保持可查看，但依赖被修改的项必须重跑。参考 LobeHub Acceptance 的报告与评审方式，不隐含接入其云端上传；本地验收材料默认留在当前已授权工作区。

## 8 暂停、停止、撤权和删除

| 操作 | 即时阻止 | 已在进行的工作 |
| --- | --- | --- |
| 暂停职责 | 新摄取、新研判、新接单 | 已接受任务按独立授权继续；界面提供同时停止关联任务的选项 |
| 停止任务 | 新派工、续跑、未发出的副作用 | 向运行传递取消；返回 cancelled / completed / unknown 的实际结果 |
| 撤销授权 | 绑定该授权的新副作用 | 尽力取消已发请求，无法撤回的结果需显式显示 |
| 删除 Bot | 旧 BotKey 的新操作 | 排空、撤权、索引清理；同名重建使用新代际 |
| 遗忘来源数据 | 新使用以及可管理副本的传播 | 复用现有遗忘流程覆盖新核心、outbox、证据缓存；外部已送达副本显示边界 |

取消请求返回不等于执行已停止。UI 必须保留取消中的状态与最终回执，不能立即把在途未知动作隐藏。已接受的业务任务若需要恢复，重新检查当前权限、预算、版本和来源事实。

## 9 通知、反馈与改进

通知只在以下变化触发候选呈现：需要用户决定、交付可验收、有实质变化的阻塞或用户预订的摘要。普通进度留在任务页。用户在线查看任务时优先更新页面，避免同一内容同时弹窗与外发。

M1 的站内待办不依赖 IM。M3 外部渠道复用现有 Notifications 和精确数据出站批准，按稳定 operationId 对账；未知发送结果不自动换新 ID 重发。产品上的“通知我”不能成为任意资料外传的授权。

反馈区分五种：本次成果问题、发现误报、漏报、打扰过多、长期偏好/Skill 改进。前三者进入评估集和同任务返工；后两者生成可预览差异，显示预计影响、适用 Bot/职责、验证结果和回滚方式。权限扩大始终通过显式设置完成。

“已采用”表示版本化配置生效，“有效改进”需要后续未见任务上的结果支持。不能把写入记忆或生成 Skill 文件宣称为自我进化成功。

## 10 发布与降级体验

新能力默认关闭，旧 Bot、群、记忆和 schedule 数据不做无条件迁移。协调服务不可用时继续现有聊天和管理功能，工作台显示最后快照时间与不可执行原因，不展示为无任务。暂停期恢复需先对账，过期事件不能成批突然执行。

本地版清楚显示“需要 DSH Host 运行”。应用退出/机器休眠不会继续处理；恢复后优先去重、合并和核验。未来常驻部署是独立交付，有配置、进程监管、备份和升级验证，不能靠前端开关宣称已支持全天候服务。

每次发布的能力表分别列“已实现、已通过哪些验证、哪些范围未覆盖”。正式打开 auto 的前提是任务类型通过相应授权、恢复、数据与业务验收，不以总体测试数量替代逐能力证据。
