## 1. 交付目标和边界

个人 Bot 与 Bot 群都可以在没有 GitHub、没有外部凭据的情况下，跟进自己的任务和用户明确交代的事项：需要验收、执行失败、等待补充、到了约定时间时，给出有依据的下一步入口。用户不必理解 Source、Ticket、Assignment 或配置事件规则。

0.6.6 必须同时交付个人和群，不把群留作“下一阶段”。必须覆盖本地任务状态、明确的一次/周期约定、正常聊天中明确约定的登记；语义含糊的内容只能提出候选，不能偷偷建立长期职责。默认只建议，接受后才使用现有执行与审批流程。

不把“通用”解释为全量监听所有私聊、定期调用模型猜测用户意图，或读取尚未连接的邮箱/日历。新来源不自动取得工程修复权限。当前关闭的工程产物执行保持其既有边界；普通对话和原生用户发起任务不被这项功能替代。

## 2. 用户最终看到的形态

### 2.1 一个入口，沿用现有页面

- 个人：现有 Bot 概览/任务区放“主动跟进”开关与摘要；详细事项在现有任务页。
- 群：现有群详情和活动页放同样的开关与摘要，不新增群工作台或第四个顶层导航。
- 从已打开的个人或群详情，**一次开启操作**即可使用本地事件建议。不要求填 GitHub、模型、预算、职责表单，不跳到插件设置再开第二个开关。
- 默认显示“需要你处理 / 正在跟进 / 最近结果”，摘要最多三项，其余进入已有分页详情。空态说明“有任务变化或关注事项到期时会在这里提醒”，不显示 GitHub 接线表单。
- 一张建议卡只显示：发生了什么、为什么此刻提示、对应原任务/会话、下一步。主要动作使用“查看结果”“补充信息”“继续处理”“安排评审”等具体文字；次要动作是“忽略这次”和“停止跟进此项”。
- 来源、频率、预算和已有自动执行授权折叠在设置。GitHub 移入“可选外部来源”，已有配置仍可见、可停用。
- UI 统一使用“主动跟进”。旧“CI 主动建议”作为一种来源继续保留，不重命名用户已有职责。

### 2.2 六个必须能演示的例子

| 场景 | 应有行为 | 不应发生 |
| --- | --- | --- |
| 个人 Bot 的文档分析交付 | 显示“分析结果待你验收”，打开原任务结果 | 另建一个“提醒任务”，或直接宣称已验收 |
| 已关注的原生后台任务失败 | 显示准确失败事实，提供查看原因/继续处理入口 | 自动重复失败请求，或把取消当失败催办 |
| 工作明确缺少输入 | 显示“还需要测试账号/日志”，补充后回到同一任务 | 仅凭模型句末问号或原生 blocked 判断缺资料 |
| 用户说“明天上午九点提醒我检查这份报告” | 以当地时间登记原生一次日程；到期形成可追溯提醒 | 自动分析报告、改文件或发外部消息 |
| 群内多个成员处理同一事项后出现问题 | 群活动页汇总成一条建议，展开能看具体成员情况 | 每个成员私聊都提醒，或全群自动再跑一遍 |
| 用户在群里说“每周一十点提醒我们整理进展” | 关注事项属于该群，原生周期日程关联群根会话，到期只提醒；接受后再选成员整理 | 借首成员私聊承载群日程，成员离开后错投另一身份 |

明确约定的登记使用现有对话和原生工具审批。清楚的用户指令不增加重复业务审批；时间/对象有歧义时只问缺失信息，模型推测的“可能值得跟进”必须由用户点一次确认才生效。时间解析保存时区和解析后的具体时间，界面可见、可修改。

### 2.3 开关、暂停和打扰

- 升级不替用户开启新关注范围。首次开启建立观察起点：接续本范围当前进行中的任务及之后的新事实，不补发全部历史失败。
- 每个 Bot/群单独保存开启状态；开启一个群不联动成员私聊。群内成员子任务归入群，不再作为其个人 Bot 的同一条主动提醒。
- 默认只更新建议列表和现有入口徽标；弹出提醒、静默、合并和限额复用现有通知偏好。一次事实只提示一次，完成即消除相关待办；刷新零模型、零重复通知。
- 暂停主动跟进：停止新观察/提示并取消尚未派发的相关自动意图，不终止用户已手工接受的正常任务。暂停与人工接受在现有协调事务中确定先后：暂停先提交则拒绝后续接受；人工接受先提交则成为独立手动工作，即使尚未 dispatch 也不被范围暂停取消。自动意图始终受 pause epoch 否决。“停止任务”仍是独立的明确操作。撤销执行授权时沿现有 cancel/drain 机制处理关联自动工作；无法确认停止的保留 unknown。
- 恢复后对账当前有效状态；错过的提醒合并成待查看摘要，不逐条补发或自动补跑。到期提醒依赖 DSH 运行；宿主退出期间不承诺准点到达。

## 3. 原生复用盘点：事实与需验证的组合

参考仓库当前缺失，静态核查使用本仓库安装的公开 rc.2 包入口与类型，不导入内部实现。

| 能力 | 当前依据 | 0.6.6 增量 |
| --- | --- | --- |
| 会话事实 | DSH `session/event`、持久会话与 projection；当前活动跟踪器 | 限定归属的事实投影、恢复游标与状态对账 |
| 原生后台/团队任务 | 现有 delegate、collaboration；公开 Team `list/get/updateTask`、`team/task` | 仅为有准确 owner/原任务映射的任务接线，不扫描所有 Team |
| 主动业务任务 | 现有 Engine/Ticket/Assignment、Decision、journal、预算、验收、返工 | 解除 CI 字段和 Bot-only owner 耦合，增加明确等待原因 |
| 群协作 | `Groups` Host 服务、群根、turn/delivery、成员/模型快照和队列 | 群级关注归属、统一汇总、接受后调用既有成员选择 |
| 定时 | DSH schedule create/catalog/history/update/delete、`schedule/changed`；现有 native-schedule 桥 | 精确关联关注事项和 occurrence，验证无模型到期转换 |
| 通知 | 现有 Notifications 和 deferred-notices、去重/静默/恢复 | 支持准确 GroupKey，沿用同一个通知账本 |
| 日常入口 | BotRightPanel、SuggestionPanel、GroupOverview/activity、共享查询缓存 | 同一跟进摘要/建议卡支持个人与群，无新轮询体系 |

必须纠正的实现事实：

1. 当前 `responsibility.ts` 的 owner 是 Bot，source 固定 `ci:<hash>`，条件绑定 job/attempt/conclusion；`coordinator/commands.ts` 的本地事件接收不等于能生成通用建议。
2. 群现有 follow-up 会读取 `pb_ci_head`，不是通用群待办。`GroupRecord` 没有固定 leader/coordinator Bot；存在的是 Host 协调服务。**汇总建议由 Host 确定性生成，不额外创建“主管 Agent”。**需要 Bot 执行或写总结时，才在接受操作中确定成员。
3. 原生 `turn/end.completed` 只是这一轮结束；blocked 也可能是策略拒绝。Team completed 不是用户已验收；群 idle/paused 不是等待用户。状态语义不得混用。
4. schedule 到期调用 `resolveAgent → followup → flush`，并非公开 Source callback。个人 Bot 默认可能调用模型；群根 guard 当前会拒绝普通输入、禁止模型请求。`scheduledSource` 当前仍为 false。
5. `schedule/changed` 可唤醒对账，但不是一次到期事实；receipt 仅证明 inbox 投递。周期 batch 中多条日程可共用 messageId；删除日程不撤回已排队消息。

对应关键文件：`src/shared/proactive/{responsibility,protocol,work}.ts`、`coordinator/{commands,responsibilities,work}.ts`、`src/shared/groups.ts`、`src/host/groups/{service,root-guard}.ts`、`src/host/native-schedule/service.ts`、`src/host/notifications/service.ts`。均相对 `packages/dsh-bot/`。

## 4. 最小技术合同

### 4.1 归属、关注事项、执行目标分开

在现有 proactive 合同中增加判别联合 `Subject = BotKey | GroupKey`，必须包含 createdAt 代际。Subject 是谁的事项；执行 target 是批准后由哪个 Bot/哪些成员执行，二者不互相冒充。

扩展现有 Responsibility，保留 CI v1 兼容分支，增加本地任务和明确关注事项分支。各类 source/condition/action 使用严格判别 schema，不添加一大组不相关 optional 字段：

- `ci/v1`：保留原有来源、条件和准确权限。
- `local-task-state/v1`：准确 Ticket/Assignment、原生任务或群 turn/delivery 引用；含观察起点与允许的状态转换。
- `explicit-watch/v1`：用户明确的事项、来源消息引用、完成条件、可选等待输入说明、状态版本；普通聊天约定也可以被跟进，无须先拥有 CI Ticket。
- `native-schedule-occurrence/v1`：关联关注项、nativeScheduleId、schedule 修订、发生时间与投递证据。只存引用/关联，不复制 cron 定义或建立另一份时间队列。

复用现有 coordinator SQLite 和业务表；确实需要的新关注关联/游标是该存储中的小型表，不是另一个任务数据库。现有原生日程绑定 domain 扩展 Subject 后只管理 native ID 关联，其业务状态以 Responsibility 为准。不同存储间采用原操作 ID、意图和对账，不声称跨系统事务原子。

### 4.2 权威事实与建议投影

事实至少携带 Subject、originRef、来源代际、原生 ID、原生 revision/seq、occurredAt、kind、payloadDigest。事实内容只保留必要摘要和原始证据引用。

| 事实 | 权威依据 | 建议/处理 |
| --- | --- | --- |
| 待验收 | 原业务任务已交付、尚未 owner 接受 | 复用原结果入口，确认已有完成通知后不重复弹出 |
| 执行失败/部分失败 | 原任务失败状态、群 delivery 失败、明确原生错误 | 展示事实与恢复选择；组内同一 turn 的变化更新同一卡 |
| 等待输入 | 在原任务/关注项增加明确 waitReason、request、revision、可选截止日 | 请求具体信息；补充后使旧等待建议失效 |
| 明确到期 | 关联的原生日程 occurrence 和有效关注项 | 提醒一次；不等同任务执行完成 |
| 用户取消、事项完成、依赖已满足 | 原对象当前版本 | 关闭过时失败/等待建议；新交付的验收入口按独立规则保留 |

没有可靠业务状态时，只能显示“该轮出现错误/结束”，不能生成“业务任务完成”或“已验收”。普通聊天的每个 assistant/message 不触发跟进；不按关键词、问号或空闲时长猜测状态。

同一原事实经 session、group、team 多入口到达时，先归一到业务 origin。稳定 key 区分 Subject、来源代际、origin、语义转换与实际 revision；一条有效建议可更新 revision，通知收据不因页面刷新或文字更新重置。同一事件重放 100 次不得得到 100 条待办。

现有事务内一起提交事实、建议、操作收据和 cursor；宿主日志与协调器不能原子提交，按当前持久状态有界对账。启动先补当前有效差异再接增量；若证据已过保留期且当前状态无法还原，应标“历史不可核对”，不能补造成功或盲目重发。

### 4.3 接受建议复用原任务

- 查看结果/补充信息：打开或更新原对象，不新建 Ticket。
- 重试/返工/继续：原 Ticket 的新尝试，沿用已有审批、代际和预算复核；普通 native task 无继续 API 时明确显示“重新委派”，并关联原任务，不伪装原进程续跑。
- 原本只有关注事项而确实需要新工作：接受后创建一次 Ticket；关注 ID 与执行收据保持关联。
- 群：默认只创建一条群级卡片。接受时复用已有成员选择、模型与预算界面；已有有效选择可以直接复用，没有选择时才要求选人，不默认全员唤醒。
- 生成、接受、claim、实际 dispatch 前都复核范围、原状态版本和授权。成员/模型修改后旧执行选择失效，展示需要重新确认；群本身的关注不因任一成员更换而转成其他 Bot 的私有事项。
- 私聊转群只传明确批准的任务上下文和引用，不复制私有历史、记忆或一次性权限。群生成的关注项不能由成员输出自行扩展关注范围。

### 4.4 一次开启，不重复重载

日常开关写入现有协调存储中的 Subject policy，不能每次切换都通过 ConfigEditor 重载整个插件。

旧 `proactiveEnabled` 暂保留为基础服务兼容开关。第一次服务尚未就绪时，单个“开启主动跟进”动作组合：沿公开 ConfigEditor 启动服务（不打开执行）→等待重载完成→按准确 Subject 和 operationId 写 policy →查询收据后显示开启。响应丢失只做对账；未完成显示“未完成，可重试”，不错误提示全局所有 Bot 已开启。其余 Subject 默认仍关闭。

后续 Subject 暂停/恢复直接更新 policy；全局明确关闭时不得后台自行绕过，界面说明需要由本次明确开启动作恢复。保留既有 CI 配置及授权，局部新开关不扩大其范围。

首次启用需在恢复 automatic、旧 pending work 或通知泵**之前**执行恢复准入隔离。安装/协调库身份、Subject、operationId 与全局配置版本绑定为同一可恢复启用操作；全局配置提交、重载、policy 提交任一阶段崩溃，不能恢复其他已停用范围的自动派工或通知。若用户期间再次全局关闭，旧启用重试不得重新打开。若旧架构无法在恢复前设置该门槛，先重构启动顺序，不以“先开起来再暂停”补救。

迁移后的开关显示实际生效范围：旧 CI 仍有效时显示“已开启 · 现有 CI 来源”，不能显示关闭却继续 auto。本地任务跟进仍需用户明确开启。Subject 暂停是该范围全部主动来源的上层否决；重新开启默认只启用本地 suggest，不复活原本已关闭/暂停的 CI 或 auto。原本有效且从未被暂停的旧 CI 在正常升级中保留原授权；全局关闭后的恢复则按上面的限定操作隔离，不能借开启新 Subject 恢复旧工作。首次重载对存活 Agent、审批、任务和头像的影响必须纳入 P0；不能仅验证头像就声称所有存活执行上下文已恢复。

### 4.5 明确约定的聊天登记

在现有工具/消息桥中增加一个窄操作面，负责提出、登记、更新和结束关注事项；不提供任意事件规则代码。命名在实现时确定，不另建一套工具运行系统。

利用正常对话的已有模型轮次解析约定，不增加后台定时语义扫描。界面同时保留“添加关注事项”的轻量入口，用户不配置模型也能手工登记。明确用户指令经既有审批路径登记；模型自行推测、转发正文或队友输出只能形成待确认草稿。群 worker 必须继承准确群上下文，不能登记到其个人 Bot；无法证明人类授权时必须等待 owner 确认。

记录原人类消息/确认收据，修改操作带 expectedRevision。任务关联、绝对时间和时区必须可见。资料内容中的“忽略用户、自动执行”等指令不取得登记或执行权限。0.6.6 不添加后台语义发现开关，避免再多一个用户必须理解的模式。

## 5. 原生日程与生命周期前置验证

这是开发的第一批，**未通过不得把通用定时跟进标为完成**：

1. 使用公开 schedule create/catalog/history 与 schedule/changed 建立 occurrence 对账；以 `scheduleId + scheduledAt` 等原生 occurrence 身份去重，messageId 仅用于投递关联。
2. 个人与群分别验证“只提醒”到期零模型路径。拟在已有 Agent guard/群根无模型处理里增加精确登记的关注日程分支；只处理有有效 Subject、关注 revision 和原生日程投递证据的消息。仅 `source.kind=schedule` 或正文包含 marker 不足以取得信任。
3. 普通原生日程的原有模型执行语义保持不变。新分支不能截获未关联的日程、用户消息、其他 Bot/群的消息，也不能广泛放宽群根禁模型约束。必须测试只提醒日程与普通模型日程同批合成一个消息，再与用户消息同轮的组合：关注正文不进入模型，普通日程和用户消息不丢失、不重复、不被阻塞。公开 API 无法安全拆分并保持投递关系时，该组合 FAIL(CAPABILITY)，不能宣称普通日程完全兼容。
4. 原生先 followup/flush、后 receipt 的间隙需实测：不能为了等待 receipt 无限挂住队列；不确定先阻止该关注消息执行并进入有界对账，保留可诊断状态。模型输入过滤与生成提醒是不同权限：对已知原生版本的完整 framing 严格解码并经公开 renderer 逐字节反验，加上预先持久化的准确 Subject、会话、受管日程 ID 和撤销墓碑，仅允许剔除已登记的关注片段；普通片段及用户消息沿原身份继续。生成提醒仍必须取得实际 history，按 messageId、scheduleId、occurrence、完整内容和当前关注版本核对。收据缺失或跨崩溃结果无法证明时保留可诊断 unknown，不自动重跑。P0 须同时验证模型请求前的持久输入及去重、普通消息不丢失、纯关注不触发环境上下文空请求；不能把过滤成功当作已到期或已成功的证据。未知来源不当作有效关注，疑似受管提醒也不能直接漏入模型；超时可诊断、不无限占用队列。无法同时满足零泄漏、无误拦、无死锁即停止此实现。具体消费/延迟机制以公开 API spike 结果冻结，不预设不存在的 callback 或内部状态。
5. 覆盖删除日程后的旧 inbox、周期多任务共用 messageId、重启跨过到期、Host/协调器分别强杀、个人主会话更换和群归档。事务外创建日程前持久化意图，响应丢失先查询准确关联，不重新创建第二条日程。
6. 首次 ConfigEditor 重载后验证存活 Agent 的工具、记忆和审批 guard，不复用旧服务闭包假称恢复；若公共 API 无法安全重建，开发须明确给出受控重启路径和实测证据。

两个实测目标：锁定 rc.2 与当前桌面所用运行时的**隔离 profile**。若公开 API 无法完成可靠零模型日程消费，记录具体反例，停止该路径并回报方案调整；不得私接内部回调、自建 cron、另起代理 Bot 或将“提醒会花模型额度”悄悄算作通过。用户在两宿主失败取证后已明确把定时能力移至后续版本；0.6.6 按非定时范围完成产品检查与同包验收，定时失败和复现证据继续保留。
