# Bot 首次对话与职责建立方案

状态：用户已于 2026-10-30 批准并要求实现，追加单 Bot 头像与组合群头像。实现基线：DSH-Bot 0.6.2；交付版本 0.6.3，实际验证见 [V063 验收](../acceptance/V063-onboarding-avatars.md)。

新建 Bot 后，它在原生工作区对话中主动介绍自己，根据名字提出职责假设，再通过聊天理解用户交给它的工作。用户仍然只需输入名字，可以直接交任务；长期职责在明确表达后保存，后续私聊和群聊共同使用。

本次已批准“首次开场、职责建立和生效验证”这一完整增量。主 Bot、持续关注、外部事件唤醒与无人值守协作列入后续路线，不包含在本次实现授权内。实施顺序为验证原生 API 组合、实现、回归与打包；桌面安装仍不包含在本次范围。

## 产品依据与现状

Grok 的 2026-09-08 v0.45.0 更新明确新 Bot 会自我介绍；2026-09-03 v0.39.0 明确问候使用应用语言。[官方更新记录](https://x.ai/changelog/bot)

官方创建流程是命名、进入聊天，再通过对话明确职责、信息来源和审批边界。“根据名称提出角色猜测”采用用户提供的实际体验作为设计目标，官方没有公开该行为的内部生成规则。[创建与管理 Bot](https://docs.x.ai/grok-bot/bots)

当前版本已具备以下基础：

| 能力 | 当前实现 | 本期处理 |
| --- | --- | --- |
| 仅名称创建 | `shared/schema.ts` 默认空 persona，Client 创建后打开主会话 | 保留表单，增加明确的首次开场意图 |
| 原生主对话 | `host/main-session.ts` 创建、保存并复用主 Session | 原位发言，不新建第二套聊天 |
| 首次提示 | `client/components/FirstChatHint.tsx` 只有页面提示 | 增加真实 Bot 回复，提示仅作为失败兜底 |
| 聊天保存职责 | `host/tools/bot-manage.ts` 使用现有原生审批 | 复用，并补版本与代际校验、准确的职责预览 |
| 职责即时生效 | `host/live-persona.ts` 更新后续 prompt 组装 | 覆盖私聊和群 worker，不替换历史 |
| 长期记忆 | 已有 Bot 私有记忆工具与检索 | 继续存偏好和事实，不另建职责库 |

上述 `src` 文件均位于 `packages/dsh-bot/src/`。本方案补充 [聊天精简设计](bots-chat-simplification.md) 的首次对话部分；现状以当前代码和 [V060 职责更新说明](../implementation/v060-persona.md) 为准。

## 用户流程

### 名称创建与主动开场

流程保持为“新建 Bot → 填名称 → 创建并聊天”。创建按钮附近用一句轻提示说明会使用当前模型生成首次问候，不增加必填配置。进入工作区后输入框立即可用，问候使用 Bot 当前有效模型：Bot 模型覆盖优先，其次 DSH 默认模型。

例如创建“鸿蒙迁移助手”，建议开场：

> 我是鸿蒙迁移助手。从名字看，你可能希望我协助 Android 到 HarmonyOS 的迁移，包括实现和验收。你希望我先负责哪一部分？也可以直接把第一个项目交给我。

生成规则是两三句话、最多一个问题，以应用语言开场。名称只是待确认线索，不作为已确定职责；不宣称已经读取项目、具备未连接的工具或开始持续监控。

| 创建情况 | 首次行为 |
| --- | --- |
| “周报助手”等职责明确的名字 | 提出简短职责猜测，问从哪个项目或任务开始 |
| “小鲸”等含糊名字 | 简单介绍，询问希望先帮忙做什么，不硬猜角色 |
| 本次手动新建时已填写职责 | 结合已给职责开场，不重复询问已知内容 |
| 用户抢先发文本、附件或任务 | 优先处理用户输入，跳过尚未派发的问候 |
| 从已有 Bot 复制、文件导入、预置 seed、旧版本 Bot | 不自动触发首次问候或模型请求 |
| 改名、换新主会话、重新打开、加入群聊 | 不重新触发首次问候 |

如果问候已经开始生成，沿原生停止和输入机制处理新消息，不再补发一轮过时的问候。具体取消与入箱竞态必须先通过原生 Host spike，不能仅凭 Client 状态判断用户已经优先。

### 从第一件事建立职责

用户可以直接说“先检查这个仓库”，Bot 进入工作，不要求先完成职责设置。缺少必要信息时，每次只追问与当前任务直接相关的问题。

| 用户表达 | 持久化规则 |
| --- | --- |
| 名字引出的“你可能负责迁移” | 仅留在对话中，不自动写入 persona 或记忆 |
| “以后你负责鸿蒙迁移验收，每次都看真机结果” | 使用当前 Bot 的 `bot_manage` 更新长期职责 |
| “我喜欢先看结论，记住这个偏好” | 使用已有记忆工具保存偏好 |
| “这一次检查这个项目” | 作为单次任务，不自动改成长期职责 |

用户明确表达长期职责后，直接准备拟保存的职责，使用现有 DSH 原生审批显示具体修改，不再额外询问一遍同义的“是否确认”。审批拒绝或取消时不写入，但普通聊天继续。只有持久化成功后才能反馈“已保存”。

Bot 详情增加简短的“当前职责”查看区，直接读取已提交的 persona prefix，不额外生成或保存一份摘要；长内容可展开查看。没有职责时显示“可在聊天中告诉我”，修改入口把对应提示填入当前对话输入框，不自动发送。既有完整配置入口保留。

### 在群聊中使用

私聊和群 worker 使用同一份已提交职责，不建立群专属职责表单。群内单次分工不会自动改写 Bot 的长期职责；加入群不重新自我介绍或重复设置流程。职责更新对之后开始组装的步骤生效，已经开始生成的步骤保留原快照。

主 Bot 的选择不影响本期功能：每个手动新建 Bot 都有自己的首次开场，不需要先设置一个总负责人。

## 原生能力复用与新增范围

| 需求 | 复用能力 | 插件需要增加的部分 |
| --- | --- | --- |
| 打开工作区聊天 | 现有 MainSessions、`uiWorkspace.openSession` | 区分普通打开与本次新建打开 |
| 生成真实首次回复 | 公开 `Agent.followup`、`createUserMessage`、Session/Inbox 和模型循环 | 一次性开场协调器及准确来源标记 |
| 显示触发来源 | 原生非 user context/notice 渲染 | 中英文可读摘要；仅原生显示不满足时使用公开 slot 扩展 |
| 保存引导生命周期 | 原生 `storageDomain` 和现有 Bot 存储 | 最小投递收据，不保存聊天副本或职责副本 |
| 保存与修改职责 | `bot_manage`、registry update、原生审批 | 审批预览及版本、代际冲突保护 |
| 职责生效 | 现有 live persona/system prompt section | 补私聊与群 worker 的回归验证 |
| 用户中途输入和停止 | 原生 Session 输入、停止机制 | 精确识别并结束首次开场状态 |

原生 API 已提供构件，但没有发现可直接复用的“新建 Bot 首次定位”服务，所以增加小型协调器。不会创建新的模型适配器、调度器、任务编排引擎或聊天存储。

参考源码保持 `deepseek-harness@dsh-v0.2.1-rc.2` 只读。`Agent.followup` 见 `packages/core/agent/src/runtime-types.ts:217`；`createUserMessage` 和 `MessageSourceMap` 见 `packages/llm/llm/src/message.ts:104,224`。新增 runtime import 与 peer 按真实产物评估，依赖继续精确锁定项目规定版本。

## 实现设计

### 创建意图与接口

增加面向“新建并聊天”的明确 Host 命令，建议名为 `createForChat`，包含稳定 operationId、Bot 输入和应用语言。原有 `create` 接口、模型创建、导入、复制继续保持当前语义，不因共用 create 路径自动消耗模型。

选择在同一 Bot 持久记录中增加可选、Host 所有的首次引导意图，随新 Bot 一次提交。意图至少包含 operationId、创建代际、语言及策略版本。公共 Bot patch、模型输入、导入和复制不得携带或继承这项资格。旧记录缺少该字段即不自动引导，不进行旧数据全量改写。

这样可以避免“Bot 已创建但引导资格未写入”的双写窗口。投递过程仍单独记录收据；资格与投递收据不同步时可从已提交资格恢复。创建重试复用同一 operationId，并核对原始输入与 Bot 代际，不能把名字相同的旧 Bot 当成此次新建。

登记资格不启动模型。只有该创建操作成功打开并绑定主会话后，协调器才尝试首次开场；`status`、`find`、列表刷新不产生模型副作用。创建成功、导航失败时只重试打开，不重新建 Bot。

### 首次发言与来源

使用一次构造的原生消息，通过公开 `Agent.followup` 唤醒主会话，由模型生成正常 assistant 回复。来源建议为 `dsh-bot-onboarding`，带可读 notice、BotKey、operationId 和准确输入 ID，按 strict schema 验证。

不通过固定为 `source.kind=user` 的 `sessionController.prompt` 伪装人工发言，也不直接往历史塞一段假 assistant 回复。原生 context notice 可显示简短“新 Bot 初次交流”，完整提示不作为用户消息展示。

首次轮次只做文字交流。Host 工具 guard 限制该轮不能读工作区、写职责或记忆、启动委派、创建定时任务；后续用户任务继续走原来的工具与权限路径。名字按普通数据处理，不能因名称内容改变这些限制。

现有数据流保护会将未知来源标为 unknown。接入新来源时，只认可已持久登记的准确 Bot 代际、主 Session、收据及输入 ID，继承该 Bot 的 candidate 范围，不增加人工授权，也不清除已有数据限制。仅把 source kind 加到白名单不合格。

### 投递状态与恢复

协调器只保存首次开场的运输状态，不保存“职责已确认”等第二套业务状态。职责是否存在始终读取 BotRecord.persona。

| 状态 | 含义与下一步 |
| --- | --- |
| pending | 新建资格存在；主会话可用、无用户消息后才准入 |
| dispatching | 原生输入及固定 ID 已保存，准备派发或正在核实入箱 |
| submitted | 有准确原生入箱证据；不能称为已回复 |
| completed | 找到该输入对应轮次的正常 assistant 回复与结束证据 |
| skipped | 用户已输入、目标主会话换绑或其他条件不再适合问候 |
| failed | 有明确的未投递或执行失败证据；保留 Bot 和正常输入框 |
| uncertain | 崩溃或断连后无法确定是否已执行；停止自动重放 |

收据关联 BotKey、创建操作、原主 Session、完整 nativeInput、固定消息 ID、轮次证据和时间。恢复时沿用同一个输入 ID，不再次调用构造器生成新 ID。

派发前复核 Bot 是否仍存在、代际、主会话、当前职责、是否已经有用户文本或附件。改名或职责变化发生在派发前时使用最新信息；发生在已派发之后不补发第二次问候。

正常重复打开、多窗口和重试不得重复派发。跨崩溃用公开持久日志、Inbox 与准确消息 ID 核对；无法排除已执行时保持 uncertain，不为保证“最终出现问候”而自动再调用模型。公开 followup 与插件收据没有跨存储事务，本期不承诺 exactly-once 或模型计费恰好一次。

所有资源纳入 `ctx.effect`；插件卸载、Bot 删除或同 ID 重建时取消并排空准确的开场操作，不中断其他 Bot 或用户工作。停止后不自动重启问候。

### 职责保存的并发保护

继续通过 `bot_manage → registry.update → live persona` 提交，prefix 更新保留原 suffix 和 complete。审批卡显示拟保存的具体职责，版本冲突时不允许“已保存”反馈。

当前 `bot_manage.update` 没有模型读取时的 expectedCreatedAt/expectedUpdatedAt；registry 内部 CAS 不能防止模型读取后等待审批时的旧草案覆盖。因此在同一更新路径加入读取版本和 Bot 代际前置条件，审批等待及实际提交前复检；发生冲突后重新读取，新的修改内容重新进入既有审批。

旧调用仍保持兼容，但不能绕开代际与审批快照检查。角色保存的正式路径必须携带读取版本；未带版本的兼容调用至少在准备审批时锁定快照并在执行时复核，不能声称它已保护模型更早的未知读取时点。

### 成本与失败体验

默认仅本版本明确手动新建的 Bot 开启首次问候，使用当前有效模型。建议新增 Config：`onboardingEnabled=true`、`onboardingMaxOutputTokens=256`、`onboardingTimeoutMs=30000`，提供数值范围校验。只提交一次自动开场操作，不安排周期轮询生成或应用级自动重试；底层 provider 的原生重试不等于一次计费承诺。

没有可用模型、断网、失败或超时都不撤销 Bot，也不阻止用户输入。显示一句“暂时无法主动开场，可以直接告诉我第一件事”；只有明确未执行、且仍无用户消息时可手动重试。uncertain 必须先核实，不能提供会盲目重发的重试按钮。轮次超时与取消完成的真实状态由原生执行证据决定。

## 验收标准

| 验收项 | 通过条件 | 证据层级 |
| --- | --- | --- |
| 名称创建 | 一个名称可创建并进入原生工作区，模型未配置也保留 Bot | Host 与浏览器 |
| 真实开场 | 正常 assistant 消息；触发显示为 notice；无伪造人工发言 | 原生 Session 事件与浏览器 |
| 内容质量 | 明确名称提出合理猜测；含糊名称不硬猜；短开场最多一问；名称不等于已保存职责 | 固定回放验证流程，真实模型由用户验收 |
| 用户优先 | 文本、纯附件、停止、生成中补充均不陷入引导循环，不补发过时问候 | Host 竞态与浏览器 |
| 一次性行为 | 重复打开、多窗口、创建响应丢失重试都不重复开场 | 集成与 Host |
| 崩溃恢复 | 派发前后、flush 前后、收据提交前后使用两次独立 Host 核对；不确定不重放 | 冷 Host 与持久日志 |
| 创建边界 | 导入、复制、旧 Bot、seed、换新主会话、加入群均不触发问候请求 | Host，模型请求计数为零 |
| 来源与工具边界 | 伪造来源、错代际/Session/消息 ID 拒绝；欢迎轮无业务工具副作用；后续普通输入正常 | Host 正反例 |
| 职责保存 | 同意才持久化，拒绝和取消不写；保留 suffix/complete；工具成功后才反馈保存 | 原生审批与存储 |
| 并发修改 | 等待审批期间其他窗口修改或 Bot 重建，旧草案冲突而非覆盖 | Host 与版本断言 |
| 私聊群聊一致 | 下一次组装使用已提交职责，当前正在生成步骤保持快照，历史不丢 | 主聊与群 worker |
| UI 与生命周期 | 中英、亮暗、宽窄屏；输入框持续可用；卸载和取消无重复监听或迟到写入 | 浏览器与生命周期测试 |
| 兼容交付 | 既有 Remote、旧数据、职责、模型选择与群聊回归通过；包与安装摘要一致 | `scripts/pnpm check` 与隔离安装 |

自动验证只使用隔离目录 `DSH_HOME="$PWD/.dsh-dev"` 和 synthetic/loopback 模型。它证明原生机制与界面，不证明真实模型能始终给出合适的职责猜测。当前项目规则禁止启动需要模型 API key 的真实会话，这部分保留给用户最终体验验收。

## 后续主动助手路线

完成本期后，再独立评审“已确认职责如何驱动持续行动”：

| 增量 | 拟采用方式 | 与本期的区别 |
| --- | --- | --- |
| 主 Bot | 从已有 Bot 指定一个主要联系人，汇总和协调 | 本期所有 Bot 的首聊不依赖该角色 |
| 持续关注 | 用户通过聊天明确关注对象、触发条件、行动范围和结果落点 | 名称猜测与职责保存都不会自动创建关注任务 |
| 定时与事件 | 复用 schedule、webhookRuntime 及可用 provider，补去重和状态 | 本期不新增后台轮询或外部事件接入 |
| 群内主动协作 | 在预先授权的任务范围内调用现有子代理与群运输 | 现有后台委派保护不在本期放宽 |
| 常驻执行 | 单独评估持续运行的 DSH Host 与通知渠道 | 本地桌面退出后仍运行不在本期保证内 |
