# DSH Bot 创建管理与群聊精简方案

实施记录：本方案后续已进入 `0.6.0` 实现，最终功能、命令、安装包与运行证据统一见 [V060 验收](../acceptance/V060-simplified-bots.md)。下文“此轮交付”“未执行”属于原设计阶段记录，不替代后续验收状态。

日期：2026-10-29。对照基线：当前 `0.5.1` 工作树，`phase/deepening`，HEAD `b4cd01d`，包含已有未提交实现。此轮交付为设计；不修改产品行为或桌面安装。参考以 Grok Bot 官方文档为准，不包含本机 Grok 界面实测。

建议把日常入口收敛为聊天：创建 Bot 只填名称，创建后通过消息交代职责；点击 Bot 或群直接进入 DSH 工作区；群消息通过输入框内的 `@` 和消息上的“回复”定向。原有能力继续保留，但按需要出现，配置与诊断退出日常聊天主界面。

[交互演示](bots-chat-simplification.html)展示建议的信息层级和主要动作，使用示例数据，不连接模型或真实 Bot。尺寸、颜色与布局是 DSH 适配设计，不声称复刻官方截图。

## 官方流程与采用范围

| 官方流程 | 本次采用方向 |
| --- | --- |

| 应用级设置与会话资料分开，模型由产品管理。[设置](https://docs.x.ai/grok-bot/settings-and-notifications) | DSH 采用宿主默认模型，保留有实际需求的 Bot 模型覆盖，默认收起。 |
| 多 Bot 可并行、互相交接；云端执行可在客户端关闭后继续。[概览](https://docs.x.ai/grok-bot/overview) | 延续现有原生后台执行，明确本地 Host 生命周期；界面精简不等于获得云端持续运行能力。 |

官方页面对群聊审批描述不一致：协作页称审批请求不在群内出现，[审批页](https://docs.x.ai/grok-bot/approvals-security-and-privacy)又描述群内审批归属。这里不据其中任一页承诺完全复刻；DSH 保持原生审批语义，群内只显示有明确归属且公开 API 支持的内容，必要时跳转执行会话。

上述下拉是选择被回复的历史消息，不是收件人列表；但与单独勾选成员共同造成了用户指出的表单感。两处都应精简。

`natural` 路由当前会唤起所有可用成员，同时已有 `group_message(action=skip)` 允许不发言。因此缺口不是从零实现“自主回应”，而是验证选择性回应、减少冗余内容，并让 UI 不把每个执行都显示成一张任务卡。官方未公开内部调度算法，不能由它的界面推断一定只调用一个模型。

## 对话入口与管理收敛

Bots 入口显示最近私聊与群聊，可以搜索、置顶；点击直接通过原生工作区导航打开。右上只保留“＋”，菜单含“新建 Bot”和“新建群聊”。已有 Bot 主会话和群 root 继续使用，不因界面调整新建副本。

优先把这一轻量列表接到现有公开侧栏扩展；若宿主不支持统一排序，就在 Bots 入口页提供同一列表，点击仍打开原生工作区。不重做 DSH 整个侧栏，不再建立一套插件内部聊天记录或第二个聊天页面。

会话顶部显示头像、名字、简短状态和更多。点击名字打开详情侧面板：

- 资料：名字、头像、可选标签；不展示内部 ID，复制标识放诊断中。
- 工作与文件：当前会话相关的执行、定时工作和结果；无数据时不铺空面板。
- 更多：置顶、隐藏、重命名、兼容设置、删除。

隐藏、暂停、删除是不同动作：隐藏只改变列表可见性；暂停针对具体工作；删除沿用现有确认和数据处理规则。不能通过“隐藏”暗中停止任务，也不能通过简化确认改变旧版本的数据删除范围。隐藏入口应有可找到的恢复列表；分区、模板共享等可在核心流程完成后追加。

全局设置负责应用连接、通知、IM 和维护诊断。定时工作优先链接原生任务页；记忆图谱、迁移和共享策略归入高级维护。日常聊天里不再同时出现“后台任务、定时任务、消息概览、能力、会话历史”五块面板。

## 创建 Bot 以及在聊天里建立职责

默认路径：`＋ → 新建 Bot → 输入名称 → 创建并聊天`。自动生成头像，点头像才展开选择；名称之外没有必填设置，也不把“职责”换成另一个必填表单。

创建成功后直接打开可输入的 Bot 主会话，空态给一句引导：“告诉我你希望我负责什么，或者直接交给我第一件事。”可以提供填入输入框的示例；示例不会自动发送。创建失败保留名称；创建成功而导航失败只重试打开，不重复创建。

源码上新建要求 `{ id, name }`，其他多数配置有默认值；UI 可生成稳定 ID 并在同一次提交/恢复中复用。ID 不跟随改名变化。创建结果不明时先核对既有记录；如现有接口无法可靠区分已受理与未受理，再补精确的创建幂等契约。打开或取消创建弹窗不应提前留下空工作区。

“用聊天教职责”需要区分两种保存：

| 用户表达 | 处理方式 |
| --- | --- |
| “以后汇报尽量简短，记住这个偏好” | 复用当前 Bot 的 `bot_memory_save/search/list/forget` |
| “从现在起你负责竞品研究，每次结论都附来源” | 通过现有受审批的 persona 更新路径保存持久职责，并给明确保存结果 |
| “这一次先帮我看看这份报告” | 普通任务上下文，不自动变成永久职责 |

当前记忆注入明确将其视为参考数据，并受长度配额影响；把职责只塞进普通记忆不能保证持续生效。职责更新应只改当前 Bot 对应字段，展示改变内容，允许修正；仍走原生审批，不借此放开工具、模型、目录或连接器权限。

当前 `bot-manage.ts:248` 明确更新适用于新建或冷恢复 Agent，存活 Agent 保留原配置。因此“聊天设定后立即生效”需要新增公开 API 适配，不能只验证数据库保存。先 spike 原生提示上下文更新的生效边界，再实现明确的生效反馈；若暂时只能下一次恢复生效，必须如实说明，不静默更换主会话或丢弃历史。旧的完整人设、禁用记忆等特殊配置保留并说明影响。

兼容设置只在主动打开时出现。第一层是模型覆盖、能力和工作目录；再展开高级项才看到基础模板、suffix/complete、注入上限、工具限制等。表单只更新实际改动的字段，隐藏字段不得被默认值覆盖。记忆维护页保留作为检查和恢复入口，不在日常详情中常驻。

## 群聊交互与布局

建群只需选成员，自动生成可改群名，然后直接打开工作区聊天。2个成员起，最大人数遵循当前配置；目录、执行顺序和旧模式放兼容设置。创建处选择成员是必要步骤，发送每条消息不再重复选择。

```text
Bots                     竞品调研                  3 位成员   ···
搜索             ＋      ─────────────────────────────────────
                         研究员                         10:24
● 研究员                 已找到两份发布说明，变化主要在定价……
  写作助手
  审阅员                 审阅员                         10:25
▣ 竞品调研               第二个结论还缺公开来源。

                         你
                         @研究员 补充来源，@审阅员 再检查一次。

                         研究员正在处理 · 另有1项工作
                         ┌ 回复 审阅员 · 第二个结论……       × ┐
                         │ 输入消息；键入 @ 提及群成员        │
                         │ ＋                            发送 │
                         └────────────────────────────────────┘
```

这是布局示意，不是对官方视觉样式的断言。建议正文最大宽度约760px，随宿主实际对话宽度协调；头像约28px，姓名与正文左边缘对齐。移除每条普通消息的大边框和多层卡片，主要用间距区分作者；时间弱化，操作在悬浮、键盘聚焦或移动端更多中出现。文件、问题、错误保留适当容器。

输入框固定在对话底部，自动增高，默认只有附件入口与发送按钮。回复条在需要时出现；成员候选贴近光标或输入框有效位置，不遮住正在输入的文字。群成员详情从标题打开，不常驻成员列表、模式说明、执行序号和路由提示。亮暗主题均使用 DSH `--dsw-alias-*`，避免把装饰色当成员身份的唯一线索。

### 发送语义

| 输入或动作 | 目标与反馈 |
| --- | --- |
| 普通消息，无引用无提及 | 延续 natural 群语义，成员可以回应或 skip；不制造每人必须交一份答卷的体验 |
| 输入 `@` | 当前群成员候选出现；输入名字过滤，方向键移动，Enter/Tab 选择，Escape 关闭 |
| 选择一个或多个成员 | 文中出现可识别的提及片段，发送至准确 memberId，不要求提及出现在句首 |
| `@everyone` | 作为保留的全体选项，按发送时成员快照解析；不与普通同名 Bot 混淆，不默认强迫每人发言 |
| 对 Bot 消息点“回复” | 输入框显示作者和摘要，默认定向原作者；发送后显示引用并可回到原文 |
| 回复同时显式 `@` | 显式提及决定目标，引用保留为上下文；避免后台又偷偷加入被引用作者 |
| 回复自己的消息，无 `@` | 只补上下文，按群原有路由；不虚构一个 Bot 收件人 |
| Bot 正在工作时发消息 | 输入可用；新工作、补充旧工作、回复问题都有明确关联，不能只把按钮解禁而丢失目标 |

候选不再搭配一个独立复选框面板。同名 Bot 用头像和可区分标签辅助选择，底层保留 GroupKey + memberId 身份。改名不改变已选目标；成员被移除、禁用或同 ID 重建时，保留失效提及并提示修正，禁止静默移除后变成全群广播。用户编辑或删除提及文本时同步更新身份，不能留下隐藏收件人。邮件地址、代码块和引用中的 `@` 不应误作发送目标。

已发送引用需要同时覆盖 Bot 消息和用户消息。前者可由当前消息投影补 `quoted`，后者需核实原生消息扩展的公开出口，不能把用户发言伪装成 Bot 发言。原文已删除或无权访问时仅显示不可用，不从其他群寻找同 ID 消息。

### 过程与成果怎样出现

运行中只显示紧凑状态，例如“研究员正在查资料”；有多个工作时可展开查看，单独停止某项。用户补充应归入所选工作；独立请求开启新工作。状态必须来自真实执行；排队、执行中、等待答复、失败不能统一写成“正在输入”。

私聊已有后台委派能力，不能据此认定群链也支持实时追加：当前 `groups.send` 受理新的 turn 和 replyTo，并没有更新正在运行的指定 worker 的接口。群内实时补充需桥接公开子代理 prompt/interrupt 能力并验证准确目标；独立工作并行还需调整按群串行调度和上下文边界。未完成这部分时，界面显示“已排队”，不宣称“已交给正在工作的 Bot”。这些是独立后端增量，不靠隐藏状态或解除输入禁用实现。

Bot 间交接以群内消息表现，后台执行细节折叠到“查看工作”。保留现有 skip、接续限制和单链停止，不新增必须指定协调者、分工表或工作流编排器。现有 `GroupActions.drafts` 已按 rootSessionId 保存草稿、附件和请求身份，直接延续，不重写成另一套状态库。

普通问题在对应消息处回答并返回提问 Bot。需要原生审批时保留原生对象及其归属；公开扩展不足时给“打开执行会话”，不把自由文本“同意”伪造成审批成功。成果在群内提供可打开文件/链接，失败贴在对应消息，重试复用已确认的请求快照，避免重复执行。

## 优先复用 DSH 的实现方式

下表是 rc.2 公开源码核查；涉及新组合的项目仍需隔离 spike。开发参考版本与实际桌面版本的差异在集成时分别验证。

| 能力 | 复用面 | 插件仍需做的部分 |
| --- | --- | --- |
| 会话与导航 | 已有 `uiWorkspace.openSession`、Host 主会话及群 root | 最近对话投影、轻量资料入口 |
| 工作区消息 | 公开 `conversation.chat.node` 与现有 group 投影 | 平铺 Bot 消息、补引用，不另存聊天历史 |
| 群输入 | 公开 `conversation.composer` chain slot | 保持精确群接管与 `groups.send`，普通私聊走原生 fallback |
| 提及候选 | `ui-input-trigger` 公开 `registerSource`、`InputTriggerController` 与引用契约 | 群成员 source、稳定身份、textarea/caret 适配 |
| 候选显示 | `ui-primitives` 公开 `MenuSurface`、定位相关 hooks、`observeComposition` | 群专用候选样式、键盘和输入法组合验证 |
| 文本与附件 | 公开 `MarkdownText`、现有 `fileUpload.upload` 和 receipt 校验 | 简化呈现、保留上传恢复与原文来源 |
| 并发工作 | 原生 subagents/jobs、已有后台任务状态 | 轻量状态、指定工作补充与停止 |
| 日程和授权 | 原生 schedule、approval、现有连接能力 | 按需引导和归属提示，不建立第二套审批/调度器 |
| 持久职责与记忆 | 现有 persona 更新和 per-Bot memory 工具 | 聊天反馈、配置生效验证；记忆不冒充指令权限 |

`ui-input-trigger/src/client/index.ts:18–32` 已公开候选控制器；不能笼统称“DSH 没有 @”。但 `ui-conversation` 根入口不导出完整 InputBar/ComposerContentEditable，`ComposerBarInjected`、键盘/editor 接口包含明确的内部边界。`matchEnter` 只处理以触发符开头的整行，不能替代所有群消息的提交路径。

因此先验证最小桥：本群专属子 scope + 成员 source + 独立公开 controller + 现有 textarea + MenuSurface，所有订阅随 `ctx.effect` 清理。不要与原生 editor 共用同一个有写入权的控制器；必须确认候选选择、文本插入、卸载和平台模块可用性。只有这个公开组合确实不成立时，才实现小型候选组件，并记录失败原因；不引入完整自建富文本编辑器或内部 deep import。

若历史中需要精确提及芯片，可以增加可选 mention metadata，兼容旧记录；发送权威目标仍是经过 Host 校验的 memberIds。先保留既有严格契约，不为纯布局改动扩大 Remote 面。若新增契约，要覆盖 strict-definition 注册与升级冷启动，避免再次出现 definition-unavailable。

## 实施顺序与验收

产品验收应覆盖以下场景，未执行项不得写成通过：

1. 新建只输入名称就进入可聊会话；再用消息设职责，当前会话与重启恢复均验证生效。
2. `@` 在句首、句中、中英文名字、同名成员、多成员及 everyone 下均选中正确身份；中文/日文输入法确认候选不误发送。
3. 删除、禁用、改名、退出群、删除后重建发生在输入中和发送中时，不误投或退化成广播。
4. 普通发送、回复、回复加 @、纯附件与切群草稿恢复；引用显示和跳回原文；上传失败可恢复。
5. 发送超时后精确重试只受理一次；请求未知时不自动刷新 membershipRevision 重发；用户改内容形成新操作。
6. 两个工作进行中仍可提问、补充和另开工作；停止 A 不影响 B；取消后迟到结果不重新启动链。
7. 私聊、非群原生输入与文件流程不受影响；旧配置、旧群模式和历史完整保留。
8. zh/en × light/dark × 宽屏/390px，键盘、聚焦、可访问标签及真实截图检查；源码或 DOM 检查不替代视觉验收。
