## 用户看到的变化

1. 个人 Bot 的任务页和群的活动页都提供“主动跟进”。一次开启准确范围，不需要 GitHub、凭据或模型配置，不另增顶层页面。
2. 原业务任务交付后出现待验收入口；明确失败、等待补充和已登记事项都有对应卡片。点击回到原结果、原会话或群活动。普通回答结束和群空闲不等于业务验收。
3. 个人聊天的事项登记、更新和完成沿原生工具审批。群工作者保持原生 `never` 审批策略，只提出待确认草稿；本人确认后关注归群，不进入各成员私聊。
4. 补充和重试保留原 Ticket 与历史。已批准但响应丢失时，刷新后仍可核对原批准并恢复原尝试，不再创建批准或任务。目标失效会在实际执行前终结为拒绝，不占住待派发位置。
5. 群失败事项可只选择一名成员继续。使用群现有的有效模型与预算，只接收本次明确填写的内容，原失败轮次作为归属引用，不复制私聊或旧提示。
6. 可忽略一次、停止一项、完成、遗忘或暂停范围。暂停先提交则不接受新的主动处理；人工接受先提交后，范围暂停不误取消该次手动工作。重新启用本地跟进不会恢复已暂停的旧 CI 自动执行。

## 复用与实现

- 复用 DSH 原生 ConfigEditor、volatile 更新及 Fiber 生命周期；Bot registry、主会话和 guard 保持稳定，主动子服务单独替换。首次开启的准确范围、配置 epoch 和恢复准入在协调器开始恢复旧工作前提交。
- 复用原生 Session 事件、子任务目录、持久化读取和 Group 记录。事实只在确认归属、代际及当前版本后进入原协调库，游标和卡片提交在同一事务中。原 Work 更新直接投影，不新造任务。
- 复用固定研究原型的 Engine、Ticket 和 Assignment，通过明确 owner 输入继续原任务；不声称这套业务核心是 DSH 新增的公开 API。
- 复用原群队列、模型选择、Agent、只读限制及执行预算。原生输入与协调器收据之间不宣称跨存储原子提交，无法证明的窗口保持 unknown；只有证明原生尚无对应 turn，才允许显式放弃未启动的旧计划。
- 群服务在生命周期内维护内存 ID 索引，后续变更精确读取；同一原生子目录只获取一次再分页消费。原 Work 每事务最多补账 100 项，卡片每页 20 项、摘要最多 3 项。没有新数据库、轮询模型、cron 或新的用户配置流程。
- 显式遗忘清理对应关注、历史 Engine 正文及受管计划，保留最小墓碑防止重投恢复。停用、卸载和热重载仅清资源；原生会话的保留由原会话功能管理。

## 遗留与后续

- **原生冷读取限制**：公开 KV/子目录 API 返回完整快照，JSONL 冷读取可能解码整个日志。当前已消除插件逐事件和逐页重复读取，未自行另建持久副本或使用内部 API。不能声称任意规模、任意冷启动的物理扫描为零；30 项/1,000 项是实际隔离验收规模。
- **已延期的定时能力**：后续需原生就绪后的可靠投递恢复，以及能区分 reminder/管理消息并携带 occurrence 身份的公开消费方式，再补齐日程矩阵。失败复现保留，不用自建调度或后台模型兜底。
- **未执行**：真实模型质量、真实外部账号/消息和日常桌面部署。桌面随附 CLI 的隔离测试不等于已安装到用户日常桌面。
- **已知旧测试**：3 个 expected fail 是 shared-contracts 的跨 Bot 修正、转述 claim 信任、伪造事实时间反例；没有把它们标为新能力通过。
- 升级和回退保留原 profile 与完整备份。schema 9 数据不能交给旧版本直接写入；回退依赖升级前备份，卸载不代表遗忘。
