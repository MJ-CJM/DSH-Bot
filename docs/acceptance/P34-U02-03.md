## 实现与决策

- 决策：复用公开 MCP 根 `Config/apply`、原生 credentials、作用域工具 guard、Agent maintenance 和原生审批。理由：U01 已通过这些 API 的组合 gate，无需自建 transport、重连器、秘密存储或审批系统。
- 决策：只关闭未通过 U01 gate 的实际 IM 适配；通知中心和 `NotificationPort` 独立实现。理由：§14 要求继续其余功能，禁止靠私有 dsh-im 工厂伪造 gate。生产没有 IM adapter；测试端口明确为 fake，不代表平台联调。
- 决策：通知工具记录本地中心，不额外唤醒模型；schedule 只支持任务显式调用 `bot_notify`。理由：原生 delivery accepted 不能证明模型完成或最终回复的唯一归属，不开启普通回复的自动结果推送。
- 决策：存储表使用 `legacy_imports` / `read_state`。理由：锁定版本的公开 `defineDomain` 只接受小写下划线标识，设计中的 camelCase 是概念名称。
- 决策：副作用意图是权威记录；通知正文保留受天数/数量限制，去重 tombstone 保留到正文删除之后。理由：清正文不能重新授权同一 operationId。过期重复操作返回 `recovery-needed`，不悄悄产生第二条发送。
- 决策：复用 Bot 身份和主会话；本轮管理的是 Bot policy。群 owner 的权威校验需与 U06 的群注册表组合，当前不接受伪造的群 owner。群通知接线留到对应群任务，不用任意字符串冒充有效群。

连接器新增 `dsh_bot_connectors` v1：definitions、assignments、legacy_imports。保存纯引用、版本及非秘密 overrides；同 Bot 重名拒绝。stdio 只接受用户选定的本地绝对可执行路径；HTTP 禁止 userinfo、query、fragment；不安装或下载 MCP。管理页可调用原生 credentials.describe/set，密码仅写入原生提供者，成功、失败、离开页签时清空且不预填；原生 namespace 不可用时引导原生设置。四个模板只是配置分类，不声称 GitHub、filesystem、browser 或 Notion 已认证可用。literal env/header 使用窄白名单；不允许凭据目的键的 literal 值、已知 token 签名和脚本表达式。

每 Agent 在创建后以 Bot 生日绑定桥；私有 child closure 不向 `ctx.plugin` 传 config。缺凭据、初始化失败有受限 reasonCode；重试必须显式请求。保存使 live Agent pending，用户请求空闲应用后通过真实 maintenance 抢占；先关闭旧 child 再解析、挂新 child。凭据/配置在连接期间变化仍保留 pending，不把旧解析结果冒充新版本。撤权 guard 立即拒绝本桥的新调用，随后在空闲边界清理；不能撤回远端已受理请求。Host 继承的同名工具不覆盖，也不因本桥撤权而被禁用。Bot 复制仅复制禁用的 assignment，不复制通知授权。

`desiredRevision = assignment.revision + definition.revision`；两者只递增，因此任一保存都会推进配置代际。凭据轮换可在同一配置 revision 下 pending，需按状态判断是否已重新解析。`ready` 表示该代际原生 child 初始化通过；工具数每次从公开工具表读取。没有导入 native connection 私有状态，因此它不是独立网络健康探针；断线和重连由原生 MCP 管理。

通知新增 `dsh_bot_notifications` v1：policies、intents、receipts、read_state。intent 同行保存预留额度、attempt 和状态；跨表 receipt 写失败不能释放额度或自动重发。`sending` 冷恢复为 unknown，丢失审批的 waiting_approval 为 cancelled；已知失败/unknown 均不自动重试。UI 的新尝试使用新 operationId、可见关联旧尝试，并重新确认。外推端口需要 checked targetDigest、精确正文和 AbortSignal；异常/超时记 unknown，只有适配器明确未受理才记 failed。平台 accepted 不表示用户已读。

可调配置在导出的 Config 与 Schemastery 中校验：connectorApplyTimeoutMs=30000、notificationDailyLimit=20、notificationCooldownSec=60、notificationRetentionDays=30、notificationMaxRecords=1000；另加 notificationSendTimeoutMs=30000（1000–120000），限制失去响应的适配器。正文上限导出为 8192 UTF-8 bytes。

## 已修正的问题与遗留

首轮运行暴露并修正了原生 domain 表名限制，以及一个 Typert service 不能跨 namespace 的绑定限制：通知 Remote 现在有独立 service/namespace。冷 Host 可能已恢复 live Agent，因此测试更换 loopback URL 后必须显式 applyIdle，不能假定保存已应用。回归还补测了打开第二个 Agent 不污染现有 runtime 状态，以及 namespace 冲突时 guard 不误伤继承工具。

仍需在允许 Chromium 启动的环境重跑亮/暗截图和实际操作；中文交互目前是 DOM 证据，浏览器脚本当前截图矩阵为英文。实际 IM 目标绑定/checked send 接 U04；真实平台凭据及 Electron 系统通知不在本轮已验证范围。通知存储只保证本 Host 串行准入，不能宣称跨 Host JSON 事务或 exactly-once。第三方 MCP 自身可能在 native 日志中回显秘密；本桥不附原始异常，但不能替任意第三方服务承诺日志永不泄密。
